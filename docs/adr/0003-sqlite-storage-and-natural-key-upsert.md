# 0003 - Local SQLite via Raw `sqlite3`, Append-Only Migrations, Natural-Key Upsert

> **Status:** Accepted
>
> **Date:** 2026-09-29 _(recorded retroactively; in force since the core scaffold, `6d57d06`; migration 2 added `methodology_notes`)_
>
> **Supersedes:** _(none)_
>
> **Superseded by:** _(none)_

## Context

LangRank is a single-user CLI that builds a local history database of tens to hundreds of
thousands of observations. It needs durable storage that:

- works with zero setup on a laptop or CI runner (no server process, no credentials);
- supports ad-hoc SQL inspection by users (milestone 0005 plans inspection views);
- makes re-fetching idempotent - running `langrank fetch all` twice must not duplicate rows,
  and a source revision must update the existing row, not add a second one;
- can evolve its schema without breaking databases users already have.

## Decision

1. **Storage is a single SQLite file** at the resolved `db_path`
   ([ADR 0007](/docs/adr/0007-config-resolution-precedence.md)), accessed through the stdlib
   `sqlite3` module. No ORM and no query builder.
2. **`Database` (`src/langrank/db/repository.py`) is the only code that contains SQL.**
   Services call its methods; providers never see it ([ADR 0001](/docs/adr/0001-linear-provider-pipeline.md)).
3. **Migrations are an append-only list** of `(version, sql)` tuples in
   `src/langrank/db/migrations.py`, applied in order by `migrate()` inside a transaction per
   version and tracked in `schema_migrations`. An applied migration is never edited; changes
   ship as the next integer version. `PRAGMA foreign_keys = ON` is set on every connection.
4. **Observations upsert on their natural key**
   `(rating_id, metric_id, language_id, period_start, granularity)` via
   `INSERT ... ON CONFLICT ... DO UPDATE`. The latest fetch wins for value and provenance
   fields. `upsert_observations` returns `(inserted, updated)` for the fetch run, where
   `updated` counts only rows whose stored `raw_record_hash` differs from the incoming one -
   so a re-fetch of unchanged data reports zero updates and a non-zero count means upstream
   actually changed ([ADR 0002](/docs/adr/0002-provenance-carrying-observations.md)).
5. **Reference data is seeded idempotently** on every `Database()` construction: the language
   catalog and aliases ([ADR 0005](/docs/adr/0005-canonical-language-catalog-and-scoped-aliases.md))
   and provider metadata use the same `ON CONFLICT DO UPDATE` pattern.

## Alternatives Considered

| Alternative                                                                   | Pros                                                           | Cons                                                                                                                  | Reason rejected                                                                            |
|-------------------------------------------------------------------------------|----------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------|
| SQLAlchemy ORM + Alembic                                                      | Portable to other engines; autogenerated migrations            | Heavy dependency for ~7 tables; ORM hides the SQL users are expected to inspect; Alembic adds a second config surface | Rejected - no multi-engine requirement; raw SQL is easier to audit                         |
| PostgreSQL / DuckDB server or file                                            | Richer analytics (DuckDB) or concurrency (Postgres)            | Postgres needs a server; DuckDB is less universal for users' own tooling and adds a native dependency                 | Rejected for now - revisit only if milestone 0006 task 03.0 shows SQLite is the bottleneck |
| Flat CSV/Parquet files per source                                             | Trivially diffable; easy to publish                            | No upsert, no referential integrity, no joins to aliases/metrics without loading everything                           | Rejected - kept as an *export* format, not the store                                       |
| Append-only observation history (new row per fetch)                           | Full revision history in-DB                                    | Every query must pick "latest" per key; database grows with each identical re-fetch                                   | Rejected - revisions are detectable via `raw_record_hash` and cached raw artifacts instead |
| SQLite + raw `sqlite3` + append-only migrations + natural-key upsert (chosen) | Zero setup; idempotent fetch; inspectable; forward-only schema | SQL strings to maintain by hand; single writer; history of overwritten values lives only in raw artifacts             | **Accepted**                                                                               |

## Consequences

### Positive

- `langrank fetch` is idempotent and safe to re-run; interrupted runs leave no partial batch
  because the upsert runs only after validation passes.
- Existing user databases upgrade automatically on the next launch.
- The database is a normal file users can open with any SQLite tool.

### Negative

- Overwritten values are not kept in `observations`; recovering an old value requires the
  cached `RawArtifact` or a reparse. Milestone 0004 (archival) owns long-term retention.
- Any change to the natural key (for example, adding a `variant` or `profile` column) is a
  breaking migration and needs its own ADR.
- Handwritten SQL has no compile-time checking; coverage relies on repository tests.

## Validation / Rollout

- Integration tests (e.g. `tests/integration/test_ieee_spectrum_integration.py`) assert
  exact inserted counts and `updated == 0` for a clean load; provider contract tests pin
  `raw_record_hash` stability so `records_updated` keeps meaning "upstream changed".
- Review checklist: editing an existing tuple in `MIGRATIONS` or adding SQL outside
  `db/repository.py` is a blocking finding.
